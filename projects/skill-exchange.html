University Skill Exchange Platform

A Django web app where university students and professors trade skills and help using credits instead of money, deployed on Google Cloud.

The problem

At university, lots of people need help with something (a coding bug, a stats concept, a presentation) and lots of people are good at something. Paid tutoring is expensive and informal help depends on who you already know. There was no simple way to find someone with the right skill and give something back for their time.

The idea

A skill exchange where time and knowledge are the currency, not money. Every user starts with a fixed number of credits (for example 10). When you help someone, credits move from their wallet to yours. You can then spend those credits to get help in a different area. This rewards people who help and keeps the community collaborative.

Key features

OTP email authentication

New users verify their university email with a one-time code before the account is active. The same OTP system handles password resets.

Skills marketplace

Users list the skills they can offer, with a proficiency level, and browse skills others are offering.

Session booking

Users request and book help sessions with the person offering a skill.

Credit wallet

Each user gets a wallet automatically on signup. Credits transfer between wallets when a session is completed, so helpers are rewarded.

User profiles

Each account has a profile, created automatically, holding the user's details and skills.

My role

This was a team project with six members. My responsibilities were:

  • Backend architecture: structuring the Django apps, models and how they relate (users, profiles, skills, sessions, wallets, OTPs).
  • Credit wallet: designing and building the wallet and the transaction logic for peer-to-peer credit transfers.
  • Deployment: containerising the app and deploying it to Google Cloud App Engine.
  • Team coordination and Git workflow: organising who worked on what and running a pull-before-every-push routine during group sessions to avoid merge conflicts.

Nginx takes incoming requests and passes them to Gunicorn, which runs the Django app. Django reads and writes data in PostgreSQL, caches with Redis, and sends OTP codes through Gmail SMTP.

For local development the app runs on SQLite with Django's console email backend, so OTP codes print straight to the terminal and the whole signup flow can be tested without sending real emails.

Challenges and how I solved them

  1. Opaque 500 errors in production

    Signup and login were failing on the deployed site with no useful message. I temporarily turned on Django's DEBUG mode to see the real traceback, fixed the cause, then switched it back off.

  2. "Service Unavailable" after deploying

    The Docker entrypoint script wasn't included in the deployment manifest with the correct path, so the container never started properly. Adding it explicitly fixed the issue.

  3. Windows vs Linux line endings

    Team members on Windows were committing files with CRLF line endings, which broke shell scripts inside the Linux Docker container. I added a .gitattributes file to force LF endings so it couldn't happen again.

  4. OTP field too short

    The OTP model's purpose field was too short for values like "Password Reset" (14 characters), which caused silent failures. I resized the field to fit every purpose string the app uses.

  5. Tests not matching the real models

    Early tests referred to names that didn't exist in the code (for example UserProfile instead of Profile). I rewrote them against the actual model structure and methods.

  6. Django signals in tests

    Profiles and wallets are created automatically by signals when a user signs up, which clashed with test setup that created them manually. I adjusted the tests to work with the signals instead of against them.

What I learned

  • Deployment is its own skill. Code that works locally can fail in production for reasons that have nothing to do with the code itself (paths, manifests, line endings, environment config).
  • Read the error properly before guessing. Getting the real traceback saved more time than any amount of trial and error.
  • Tests are only useful if they match the real code, so check the models first.
  • In a team of six, a simple shared Git routine prevents most conflicts before they happen.
  • How to design a small transaction system (the credit wallet) where balances must stay correct.
